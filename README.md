# Cache Research

Учебный симулятор кешей на C++17: LRU, LFU, полная версия 2Q, ARC и LIRS.
Уровни образуют эксклюзивную иерархию: реальные данные страницы находятся только
на одном уровне, запрошенная страница продвигается в L1. Вытеснения передаются вниз.
Идеальный кеш Белади используется как эталон при той же общей ёмкости.

**Результаты исследования:** [отчёт с таблицами и графиками](results/full/report.md).
**Для разбора и защиты:** [объяснение исследовательского кода](notes/research_explained.md).

## Сборка и тесты

Нужны компилятор C++17 и CMake 3.16+. Для тестов CMake получает закреплённую версию
GoogleTest; при первой загрузке нужен доступ к GitHub. Для обработки исследования
нужен Python 3.8+, для построения новых графиков — gnuplot (проверено с 6.0).
Python-пакеты устанавливать не требуется. Готовые SVG/PNG уже находятся в репозитории.

Все команды ниже выполняются из корня проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j2
ctest --test-dir build --output-on-failure
```

Выполняются 110 проверок CTest, включая тесты политик, генераторов, исследовательской
утилиты и обработки результатов. Python-проверки регистрируются при наличии Python.

Сборка только программ без загрузки GoogleTest:

```bash
cmake -S . -B build-app -DBUILD_TESTING=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build-app -j2
```

Сборка из нового каталога с уже скачанным GoogleTest, без повторной загрузки:

```bash
cmake -S . -B build-clean -DCMAKE_BUILD_TYPE=Release \
    -DFETCHCONTENT_SOURCE_DIR_GOOGLETEST="$PWD/build/_deps/googletest-src"
cmake --build build-clean -j2
ctest --test-dir build-clean --output-on-failure
```

## Один запуск симулятора

```bash
./build/cache_sim configs/arc.cfg < data/requests.in
./build/cache_sim configs/all_policies.cfg --compare < data/requests.in
```

Обычный режим печатает только число попаданий. `--compare` печатает две строки:

```text
hierarchy_hits: 4
ideal_hits: 4
```

Это ожидаемый результат второго примера с текущим `data/requests.in`.
Ошибки выводятся в stderr с ненулевым кодом завершения.

Конфигурация задаёт число уровней и политики сверху вниз:

```text
3
ARC LIRS LRU
```

Поддерживаются имена `LRU`, `LFU`, `2Q`, `ARC`, `LIRS`.
Файл запросов содержит общую ёмкость, число запросов и ключи:

```text
2 6
1 2 1 2 1 2
```

Ёмкость измеряется в реальных страницах, а не в байтах. Для C=8 и трёх уровней
ёмкости составляют 3, 3, 2. Если уровней больше, чем страниц, некоторые уровни
получают нулевую ёмкость и сразу передают входящую страницу дальше.

Короткий пример без входного файла:

```bash
printf '2 10 1 2 1 3 2 1 4 3 2 5\n' | ./build/cache_sim configs/arc.cfg --compare
```

Ожидается 1 попадание ARC и 3 попадания идеального кеша.

## Повторение полного исследования

После сборки:

```bash
python3 scripts/run_research.py
```

Команда запускает C++-генераторы и измерения, проверяет CSV, выбирает конфигурации
по train, оценивает их на validation и строит отчёт с семью графиками в SVG и PNG.
Повторный запуск обновляет генерируемые файлы в `results/full`.
`cache_sim` самостоятельно CSV не создаёт — сохранением результатов занимается
`cache_research`, а обработкой и графиками — Python-сценарий.

Параметры по умолчанию:

| Параметр | Значение |
|---|---|
| Запросов в последовательности | 10 000 |
| Общая ёмкость | 8, 16, 32 |
| Максимум уровней | 3 |
| Конфигураций | 5 + 25 + 125 = 155 |
| Seed случайных train-нагрузок | 42, 43, 44 |
| Seed случайных validation-нагрузок | 101, 102 |
| Последовательностей | 15 |
| Отдельных прогонов | 15 × 3 × 155 = 6 975 |

Train содержит пять детерминированных нагрузок и три случайных последовательности.
Validation содержит пять детерминированных нагрузок и две случайных последовательности.
Все кандидаты для одной пары «последовательность, ёмкость» получают одинаковый вход.
Каждый кеш начинает работу пустым. Идеальный результат вычисляется один раз на пару.

| Нагрузка | Train | Validation |
|---|---|---|
| Уникальные ключи | Без повторений | Контроль без повторений |
| Горячий набор | 4 ключа | 6 ключей |
| Цикл | 33 ключа | 35 ключей |
| Горячий набор + сканирование | 4 ключа, 128 горячих запросов + 64 новых | 6 ключей, 96 + 96 |
| Смена фаз | По 8 ключей в каждой половине | По 10 ключей |
| Случайные запросы | 64 равновероятных ключа, три seed | Те же 64 ключа, два других seed |

После выбора на train конфигурация фиксируется: на validation победителя заново
не выбираем. Для случайных данных это проверка других реализаций той же нагрузки,
для изменённых детерминированных параметров — проверка переноса на другие условия.
Уникальные ключи — контроль, а не новый независимый случай.

Быстрый прогон на 720 экспериментов в отдельный каталог:

```bash
python3 scripts/run_research.py --requests 1000 --max-levels 2 \
    --capacities 8,16 --train-seeds 42 --validation-seeds 101 \
    --output results/quick
```

Пересоздать таблицы и графики из сохранённых измерений:

```bash
python3 scripts/run_research.py --skip-run
```

Без построения новых изображений:

```bash
python3 scripts/run_research.py --no-plots --output results/no-plots
```

Непосредственный вызов C++-утилиты создаёт входы, конфигурации и исходный CSV:

```bash
./build/cache_research --output results/custom --requests 10000 --max-levels 3 \
    --capacities 8,16,32 --train-seeds 42,43,44 --validation-seeds 101,102
```

Справка: `./build/cache_research --help` и `python3 scripts/run_research.py --help`.

## Какие файлы получаются

В `results/full`:

- `report.md` — итоговый отчёт. В VS Code открой его и нажми `Ctrl+Shift+V`.
- `raw.csv` — все 6 975 отдельных прогонов.
- `datasets.csv` — параметры 15 последовательностей, seed и пути сохранённых входов.
- `configurations.csv` — политики и распределение ёмкости по уровням.
- `aggregate.csv` — средние по seed и выборочное стандартное отклонение.
- `ranking.csv` — общий рейтинг, упорядоченный только по train.
- `selected.csv` — выбор для каждой нагрузки и ёмкости, его validation-результат
  и сравнение с отдельно выбранным одноуровневым решением.
- `inputs/` — точные входы. В заголовке стоит первая исследуемая ёмкость (по умолчанию 8).
  Остальные ёмкости используют те же ключи с изменённым первым числом.
- `configs/` — все 155 конфигураций; в именах `|` разделяет уровни.
- `plots/` — графики SVG/PNG и команды gnuplot, `plot_data/` — данные графиков.
- `manifest.json` — команда, версии, параметры, SHA-256 исходников, бинарника и результатов.

Пример точечного повторения прогона с C=8:

```bash
./build/cache_sim 'results/full/configs/LFU|ARC|2Q.cfg' --compare \
    < results/full/inputs/validation_uniform_101.in
```

Кавычки нужны, потому что без них оболочка воспримет `|` как канал команд.
Чтобы повторить C=16, скопируй входной файл и замени первое число 8 на 16.
В `raw.csv` для этой конфигурации, C=16 и validation_uniform_101 указаны
2512 попаданий и 5658 идеальных попаданий; распределение уровней — 6, 5, 5.

Основные метрики:

```text
hit_ratio       = hits / requests
ideal_hit_ratio = ideal_hits / requests
hit_gap         = ideal_hits - hits
gap_pp          = 100 * (ideal_hits - hits) / requests
```

Доли в CSV лежат в [0,1]. В отчёте и на графиках они переведены в проценты.
`gap_pp` измеряется в процентных пунктах. `sd_hit_ratio` — разброс между seed,
а не доверительный интервал. Общее среднее даёт одинаковый вес каждой паре
«нагрузка, ёмкость», независимо от количества seed.

## Основные результаты и границы

На текущем наборе максимальный общий train-результат у одноуровневого LIRS:
58,19%; на validation он получил 51,24%. Лучшие на train многоуровневые сочетания
выбраны для двух случайных сценариев; их validation-преимущество над выбранными
одноуровневыми решениями составило примерно 0,305 и 0,020 п.п. С двумя validation-seed
это наблюдение не устанавливает статистическую значимость.

Дополнительные уровни делят ту же ёмкость и не гарантируют улучшения. «Лучший» здесь
означает лучший среди проверенных конфигураций, при равном делении ёмкости и заданных
нагрузках. Измерений скорости, реальных дисковых задержек и расхода памяти в байтах нет.

Особенности модели: частоты LFU локальны уровню и не стареют, попадание ниже L1
сразу вызывает продвижение. Поэтому LFU нижнего уровня не накапливает частоты через touch.
У LIRS используется HIR-резерв 1% (минимум одна страница) и ограниченный стек 2C;
у 2Q — Kin=max(1,C/4), Kout=max(1,C/2) при C>0. Ghost-метаданные занимают
дополнительную память и не входят в число реальных страниц.

## Структура проекта

`include/` — шаблонные кеши, иерархия, генераторы и функции исследования.
`src/main.cpp` — одиночный запуск, `src/research.cpp` — массовые эксперименты.
`tests/` — тесты C++ и Python; `scripts/` — обработка CSV и построение графиков.
`results/baseline*` — сохранённый предварительный эксперимент из 90 прогонов,
`results/full/` — полное исследование. Старый baseline использовал Python-генератор,
полное исследование использует C++-генератор; одинаковый seed не обещает одинаковые
последовательности между разными генераторами. В обоих случаях сохранены точные входы.

Источники: [ARC](https://www.usenix.org/legacy/events/fast03/tech/full_papers/megiddo/megiddo.pdf),
[LIRS](https://xiaodongzhang1911.github.io/Zhang-papers/TR-05-11.pdf),
[полная версия 2Q](https://www.vldb.org/conf/1994/P439.PDF).
