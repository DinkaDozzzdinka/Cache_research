# Как устроено полное исследование

Этот файл объясняет новые части программы и даёт маршрут подготовки к сдаче.
Сам отчёт находится в `results/full/report.md`, команды — в корневом `README.md`.

## Общая цепочка

```text
Параметры эксперимента
        ↓
C++ генерирует последовательности и конфигурации
        ↓
C++ запускает иерархию и идеальный кеш, записывает raw.csv
        ↓
Python проверяет CSV и усредняет seed
        ↓
Выбирает конфигурации только по train
        ↓
Показывает их результаты на validation
        ↓
gnuplot строит SVG/PNG; Python формирует отчёт и manifest
```

`cache_sim` нужен для одного ручного запуска. `cache_research` перебирает эксперименты.
В обоих случаях число попаданий вычисляет одна и та же `CountHierarchyHits`.
Python не реализует вторую версию алгоритмов кеширования: он обрабатывает результаты C++.
Полный запуск: `python3 scripts/run_research.py` после сборки CMake.

## Почему 6 975 прогонов

Есть пять политик. При одном уровне вариантов 5, при двух — 25, при трёх — 125.
Всего 155. `ARC|LRU` и `LRU|ARC` различаются порядком уровней.

Нагрузки объединены в шесть семейств. На train пять детерминированных последовательностей
и три случайных с seed 42, 43, 44: всего восемь. На validation пять детерминированных
и две случайных с seed 101, 102: всего семь. Итого 15 сохранённых последовательностей.

Для каждой используем ёмкости 8, 16, 32:

```text
train:      8 × 3 × 155 = 3 720
validation: 7 × 3 × 155 = 3 255
вместе:                  6 975
```

Каждая последовательность содержит 10 000 запросов, поэтому иерархии суммарно
обрабатывают 69 750 000 запросов. Это количество работы, а не измерение времени.
Идеальный кеш запускается 15 × 3 = 45 раз: его ответ не зависит от политики кандидата.

## Генераторы: include/workloads.hpp

Все функции возвращают `std::vector<int>`. Генератор не получает ёмкость кеша:
сначала строим последовательность, затем пробуем на ней разные ёмкости.
Это сохраняет одинаковый вход для сравниваемых конфигураций.

В начале файла подключены типы размера и seed, ограничения `int`, генератор случайных
чисел, исключения и вектор. `inline` позволяет определять обычные функции в заголовке.

### CheckKeyRange

`first` — первый ключ, `count` — сколько последовательных ключей может понадобиться.
Проверка запрещает отрицательный первый ключ и выход за максимальное значение `int`.
Вычисление доступного количества выполняется через `size_t`, чтобы корректно представить
число допустимых неотрицательных ключей. При ошибке бросаем `invalid_argument`.

### GenerateSequential, строки 18–26

1. Проверяем диапазон ключей.
2. Создаём пустой вектор `requests`.
3. `reserve(count)` заранее выделяет память, но не создаёт элементы.
4. Цикл перебирает позиции от 0 до count−1.
5. `push_back(first + index)` добавляет очередной уникальный ключ.
6. Возвращаем вектор. Для count=0 он пустой.

Пример: `(4, 10)` даёт `10 11 12 13`.

### GenerateCycle, строки 28–38

1. `working_set` — количество разных ключей; оно должно быть положительным.
2. Проверяем, что весь диапазон `first..first+working_set−1` помещается в int.
3. Создаём вектор и резервируем память.
4. Для каждой позиции вычисляем остаток `index % working_set`.
5. Остатки повторяются: 0, 1, …, working_set−1, затем снова 0.
6. Добавляем смещение first, помещаем ключ в вектор, возвращаем результат.

Пример `(8, 3)` даёт `0 1 2 0 1 2 0 1`.
Один механизм используется для маленького горячего набора и большого цикла.
Отличаются размер набора и его отношение к ёмкости кеша.

### GenerateUniform, строки 40–51

1. Проверяем положительный working_set.
2. `std::mt19937 engine(seed)` создаёт псевдослучайный генератор с фиксированным состоянием.
3. `uniform_int_distribution(0, working_set−1)` задаёт равные вероятности ключей.
4. Создаём вектор, резервируем память.
5. В цикле `distribution(engine)` получает очередной случайный ключ.
6. `push_back` добавляет его; в конце возвращаем всю последовательность.

Seed — исходное состояние генератора, а не количество запросов и не размер кеша.
Внутри данного окружения одинаковые параметры дают одинаковый вектор.
Стандартная библиотека может реализовать распределение по-разному, поэтому для точного
переноса эксперимента сохраняем сами входы и контрольные суммы, а не только seed.

### GeneratePhaseChange, строки 53–67

1. Проверяем размер набора и возможность разместить два непересекающихся диапазона ключей.
2. Создаём вектор и резервируем память.
3. `middle = count / 2` — граница двух фаз.
4. Для первой половины position равна index, для второй — index−middle.
5. Остаток position по working_set повторяет ключи внутри фазы.
6. Во второй фазе прибавляем working_set: страницы первой фазы больше не запрашиваются.
7. Возвращаем готовый вектор.

Пример `(8, 2)` даёт `0 1 0 1 | 2 3 2 3`. Вертикальная черта здесь только обозначает границу.
При нечётном числе запросов вторая половина на один запрос длиннее.

### GenerateHotScan, строки 69–91

Параметры: count — общая длина; hot_size — число горячих ключей;
hot_requests — длина горячего блока; scan_size — длина блока новых страниц.

1. Проверяем положительность размеров блоков и горячего набора.
2. Проверяем запас диапазона int для новых ключей.
3. Создаём вектор, резервируем память, начальный scan-ключ равен hot_size.
4. Внешний цикл чередует два блока.
5. Первый внутренний цикл добавляет hot_requests обращений к `0..hot_size−1`.
6. Второй добавляет scan_size новых ключей. Счётчик новых ключей сохраняется между блоками.
7. Оба внутренних цикла останавливаются, если уже получено count запросов.
8. Когда размер стал count, возвращаем вектор.

Для `(13, 2, 4, 2)` результат:

```text
0 1 0 1 | 2 3 | 0 1 0 1 | 4 5 | 0
 горячие  новые  горячие  новые  обрезанный последний блок
```

Новые ключи не пересекаются с горячими и не повторяются между сканированиями.

## Перебор конфигураций: include/research.hpp

### PolicyName

`switch` преобразует значение enum в строку, пригодную для конфигурации и CSV.
Каждый `case` возвращает строковый литерал. Неизвестное значение бросает исключение.
Для `TWO_Q` строка равна `2Q`, как ожидает существующий парсер.

### ConfigurationName

Создаём пустую строку. Для каждой политики добавляем разделитель `|`, если это не
первая политика, затем её имя. Получаем `ARC|LIRS|LRU`. Это также имя файла конфигурации.
При ручном запуске путь с `|` нужно брать в кавычки, чтобы оболочка не создала канал.

### EnumerateConfigurations

`max_levels` ограничивает пространство исследования одним–тремя уровнями.
Сама иерархия поддерживает больше уровней; здесь ограничиваем размер эксперимента.

Построчная логика основного фрагмента:

```cpp
std::vector<Config> result;
std::vector<Config> current{Config{}};
```

Первая строка создаёт накопитель всех кандидатов. Вторая создаёт один пустой префикс.

```cpp
for (std::size_t depth = 0; depth < max_levels; ++depth)
```

Каждая итерация добавляет ещё один уровень ко всем префиксам.

```cpp
std::vector<Config> next;
```

Сюда складываем префиксы новой длины.

```cpp
for (const auto& prefix : current)
    for (auto policy : policies)
```

Для каждого существующего префикса перебираем пять вариантов следующего уровня.
`const auto&` читает существующую конфигурацию без копирования в переменную цикла.

```cpp
Config config = prefix;
config.policies.push_back(policy);
next.push_back(config);
result.push_back(config);
```

Первая строка копирует префикс; вторая добавляет политику; третья сохраняет новый
префикс для следующей глубины; четвёртая добавляет кандидата в общий результат.
`current = next` завершает переход на новую глубину. После цикла возвращаем result.

### LevelCapacities

Проверяем, что число уровней ненулевое. В цикле добавляем в строку ёмкость каждого уровня:
`capacity / levels + (index < capacity % levels ? 1 : 0)`.
Так же делит ёмкость `CountHierarchyHits`. Для 8/3 получаем `3|3|2`, для 2/3 — `1|1|0`.
Это диагностическая строка, она не меняет ёмкости самой иерархии.

## Запуск экспериментов: src/research.cpp

### Параметры и чтение командной строки

`Options` хранит каталог вывода, длину последовательности, максимум уровней,
ёмкости, seed для выбора и seed для проверки. Значения по умолчанию указаны в README.

`ParseNumber` использует `from_chars`: преобразует строку в неотрицательное size_t,
проверяет код ошибки и что прочитана вся строка. Поэтому `-1`, `12abc` и пустая строка
не принимаются. `ParseList` разделяет строку по запятым, читает числа и отвергает дубликаты.
`ParseSeeds` дополнительно проверяет диапазон uint32_t, который используется для seed.

`main` перебирает argv. `--help` печатает справку и завершает работу.
Для остальных опций берём следующее слово как значение и заполняем соответствующее поле.
Неизвестная опция, отсутствующее значение и нулевое число запросов — ошибки.
Проверяем, что train-seed не пересекаются с validation-seed. Затем вызываем Run.
Общий `catch` выводит исключение в stderr и возвращает 1; успешный запуск возвращает 0.

### Dataset и MakeDatasets

`Dataset` хранит идентификатор, семейство нагрузки, split, seed и параметры генератора,
а также сам вектор запросов. Seed хранится строкой, чтобы у детерминированных данных
можно было записать пустую CSV-ячейку.

`MakeDatasets` выполняет две итерации: train и validation. Выбирает размеры рабочего
набора и блоков для текущей группы, вызывает пять детерминированных генераторов,
затем добавляет случайные векторы для всех seed этой группы.
Все последовательности строятся один раз до перебора конфигураций.

### Работа с файлами

`std::filesystem::create_directories` создаёт каталоги результата, входов и конфигураций.
`OpenOutput` открывает `ofstream` и включает исключения при ошибках записи.
Поэтому диск, который перестал принимать запись, не приводит к молча обрезанному отчёту.

Для каждой конфигурации сохраняем файл: число уровней, затем их имена.
В configurations.csv дополнительно записываем распределение ёмкости для каждой C.
Для каждого Dataset сохраняем точный вход `.in`. Его первое число — первая ёмкость
из списка, по умолчанию 8. Для других ёмкостей C++ использует тот же вектор в памяти.

### Главный цикл Run, строки 153–174

```cpp
for (auto capacity : options.capacities)
{
    caches::ExperimentInput experiment{capacity, dataset.requests};
    const auto ideal = caches::CountIdealHits(&experiment);
    for (const auto& config : configurations)
    {
        const auto hits = caches::CountHierarchyHits(config, &experiment);
```

Первая строка перебирает общую ёмкость. Вторая создаёт вход с этой ёмкостью и копией
заранее сгенерированных ключей. Третья вычисляет эталон один раз.
Внутренний цикл перебирает кандидатов и вызывает моделирование.
Каждый `CountHierarchyHits` создаёт собственные пустые кеши; предыдущий кандидат
не оставляет страниц следующему.

```cpp
if (hits > ideal)
    throw std::logic_error("Hierarchy exceeded ideal hit count");
```

Иерархия с теми же ограничениями хранения не должна превысить идеальный результат.
Эта проверка выявляет несогласованность алгоритмов или подсчёта.

```cpp
const double count = static_cast<double>(experiment.requests.size());
```

Преобразуем знаменатель к double: последующее деление не будет целочисленным.
Нулевая длина запрещена в main, поэтому деление определено.

Далее цепочка `raw << ...` записывает одну строку CSV. Значения разделяются запятыми,
в конце ставится перевод строки. Политики разделены `|`, поэтому не конфликтуют с CSV.
`fixed` и `setprecision(10)` задают десять знаков после точки для долей.
После окончания перебора закрываем файлы с проверкой ошибок записи.
`run_parameters.txt` хранит параметры и сведения компилятора.

## Поля исходного CSV

| Поле | Смысл |
|---|---|
| dataset | Точный идентификатор последовательности |
| workload | Семейство нагрузки |
| split | train или validation |
| seed | Seed случайного генератора, пусто у детерминированных данных |
| capacity | Общая ёмкость в реальных страницах |
| levels | Число уровней |
| policies | Политики сверху вниз, через `|` |
| requests | Число запросов |
| hits | Попадания иерархии на любом уровне |
| ideal_hits | Попадания эталона при той же общей ёмкости |
| hit_ratio | hits / requests |
| ideal_hit_ratio | ideal_hits / requests |
| hit_gap | ideal_hits − hits |
| gap_pp | 100 × hit_gap / requests, процентные пункты |
| level_capacities | Фактические ёмкости уровней, через `|` |

Пример из validation_uniform_101: C=16, LFU|ARC|2Q, распределение 6|5|5,
10 000 запросов, 2512 попаданий, идеальных 5658. Это 25,12% против 56,58%,
разница 3146 попаданий, или 31,46 процентного пункта.

## Python: scripts/run_research.py

Сценарий использует только стандартную библиотеку Python. Его функции выполняют
отдельные шаги обработки. Лямбд и дополнительных Python-пакетов нет.

- `read_csv`: открывает файл и читает строки как словари «имя столбца → текст».
- `write_csv`: берёт названия столбцов из первой строки, записывает заголовок и все строки.
- `aggregate`: проверяет уникальность запусков и границы числа попаданий, группирует строки
  по split, workload, capacity и policies; считает среднее и выборочное стандартное отклонение.
- `choose`: рассматривает только train. Сортировочный ключ — отрицательная доля попаданий,
  число уровней и название. Минимум такого ключа означает лучший результат с разрешением равенства.
- `summaries`: строит общий рейтинг и отдельно выбирает конфигурацию для каждой нагрузки и C.
  Затем извлекает validation-результат выбранной конфигурации без переотбора.
- `validate_grid`: сравнивает множество записанных запусков с полным декартовым произведением
  последовательностей и конфигураций. Проверяет метаданные, формулы CSV и единый идеальный ответ.
- `export_aggregates`: сохраняет рассчитанные средние в aggregate.csv.
- `plot_body`: формирует команды двухпанельного графика train/validation.
- `render_plots`: записывает TSV и gnuplot-сценарии, запускает gnuplot без командной оболочки.
  Получаются шесть графиков нагрузок и общий рейтинг, каждый в SVG и PNG.
- `percent`: умножает долю на 100, округляет для отображения и добавляет знак процента.
- `report`: создаёт Markdown с методикой, таблицами, изображениями и наблюдениями.
- `sha256`: читает байты файла и вычисляет контрольную сумму.
- `main`: читает параметры, запускает C++ через subprocess, выполняет обработку и пишет manifest.

`subprocess.run(..., check=True)` запускает внешнюю программу и сообщает об ошибке,
если она вернула ненулевой код. Список аргументов передаётся напрямую, поэтому `|`
в названии файла не превращается в канал оболочки.

В режиме `--skip-run` C++ повторно не запускается. Проверяется соответствие raw.csv
зафиксированной контрольной сумме; сохраняются сведения об исходном запуске,
а текущие исходники обработчика отдельно попадают в report_source_sha256.
Если CSV получен прямым вызовом C++ без manifest, runner_command будет null:
сценарий не выдумывает команду, которой не запускал измерения.

## Как выбирается лучший результат

Сначала усредняем несколько seed внутри одной пары «нагрузка, C».
Затем общий score — среднее по 18 парам: 6 нагрузок × 3 ёмкости.
Каждая пара имеет одинаковый вес. Случайная нагрузка не получает тройной вес из-за трёх seed.

При равенстве предпочитаем меньше уровней, затем лексикографически первое название.
Поэтому среди равных одноуровневых результатов может быть выбран 2Q: это правило
порядка, а не доказательство его преимущества над другими политиками.

Train используется для выбора, validation — для последующей проверки.
У детерминированных validation-нагрузок изменены параметры, поэтому сравнение train
и validation одновременно отражает изменение условий, а не только устойчивость выбора.
У случайной нагрузки меняются только seed. Контроль уникальных ключей остаётся тем же.

Универсального «оптимального кеша» не устанавливаем. Получаем лучший вариант
внутри пяти политик, максимум трёх уровней и равного деления ёмкости на заданных нагрузках.

## Что показали числа

Одноуровневый LIRS первый в общем train-рейтинге: 58,19%, на validation — 51,24%.
Это средние по ячейкам, не число попаданий одного запуска и не скорость работы.

Для uniform с C=16 выбран LFU|ARC|2Q. Его среднее validation-преимущество над выбранным
одноуровневым LIRS — 0,305 п.п. Для C=32 выбран LIRS|2Q|ARC с преимуществом 0,020 п.п.
С двумя validation-seed нельзя объявлять эти малые различия устойчивым преимуществом.

Смена фаз особенно хорошо показывает границы вывода: на train рабочий набор 8 помещается
в C=8, на validation набор из 10 уже не помещается. Выбранный 2Q меняет результат
с 99,84% до 26,83%. Это новые условия нагрузки, а не потеря воспроизводимости программы.

## Что проверяют тесты

`workloads_test.cpp`: точные короткие последовательности, длины, диапазоны,
воспроизводимость seed, непересекающиеся фазы, уникальные scan-ключи и ошибочные параметры.

`research_test.cpp`: 155 различных упорядоченных конфигураций, число вариантов каждой
длины, имена политик, распределение ёмкости, запуск всех кандидатов и независимость повторов.

`report_test.py`: вычисление среднего и стандартного отклонения, запрет дублей и
невозможных попаданий, выбор без участия validation, разрешение равенства и веса нагрузок.

`research_smoke.py`: небольшой сквозной эксперимент на 120 строк, повторение результата
через cache_sim, побайтовое совпадение CSV при повторе, создание отчёта и ошибочные опции CLI.
При этом также сохраняются все прежние тесты пяти политик и иерархии.

Финальная проверка выполнена сборкой из нового каталога и запуском всех 110 проверок CTest.
GoogleTest при этой проверке взят из уже скачанного локального исходника.
Полный эксперимент повторён второй раз: все 6 975 строк raw.csv побайтово совпали.
